### SEED-LOG-CONTEXT — Turn seeding and logging into context objects, not singletons

There are several "static" state variables, which make the seeding (and logging) subsystem act as a module-level singleton.  All such settings should be moved into a context variable.

This is a legacy from the KPMP architecture.  

Status:

- **Status:** Pending; architectural change.
- **Next:** Map singleton state, ownership, and lifecycle first; propose a migration plan before changing code.

### SEED-ASYNC-GATHER — Implement async gather in all `async_seed.c` paths

Currently the provide only operates in synchronous mode (source gather is inline with the entropy request).  This mode will remain an option, but the default operation will be asynchronous, where background threads handle gathing from the sources and the entropy request is fulfilled from a backing ring buffer associated with each source.

This will be one of the final features added, after all tracing, debugging, and error handling have been completed.  This is to ensure the maximum available resources for the debugging of async operations.

Status:

- **Status:** Partial async/sync infrastructure exists; completing async gather across paths remains pending.
- **Next:** Inventory all `async_seed.c` gather paths and source wrappers; document which paths gather synchronously versus via worker, then complete and test the missing async paths.

### SEED-STATE — Better state handling from bottom to top

A holistic effort to improve error handling across the provider.

- Reduce number of distinct error numbers and do more with logging reasons and returning general erros reporting
- Implement ready (return entropy) vs not-ready (success with no return entropy) vs error (temporary or fatal?).
- Clearly separate controller error state from source error state(s).  Example, controller is only in error state when all validated sources are in error state.

Status:

- **Status:** Design and error-propagation work were discussed and partially implemented; current end-to-end status needs review.
- **Next:** Trace current source → async wrapper → seed control → DRBG state/error behavior, then identify missing cases and add focused tests.

## Optional Features

This list may or may not ever get done.  They are here as a point of dicussion,
to see if anyone thinks they are worthwhile enough to implement.

### RING-MODULE-WRAP — Change ringbuffer to modulo wrap detection; remove power-of-two requirement

The power-of-two requirement is fine for small buffers, but might force overly-large allocations on some systems.  For example, on some AMD-based systems, RdSeed may need to gather 90K+ bits to meet the 256-bit qualified entropy minimum.  If an admin wants the ring buffer to store 4x gathers, that's 360K+ bits, which have to round up to 512K bits to meet the power-of-two requirement.

The downside is that this would require use of a modulo operator and would slow down all operation that change the ring buffer contents.  Given the expectated usage patterns, this is probably a worthwhile tradoff, but it remains in the optional category pending further input from other contributors and stakeholders.

Status:

- **Status:** Pending design/implementation decision.
- **Next:** Compare wrap-detection options against current capacity/index invariants; benchmark the chosen approach before removing the power-of-two constraint.

### TRACE-SEED-END — Add `TRACE_END` to all seed paths

Currently, the tracing records the entry to each critical function of the seed path.  This would add a matched exit record, and implement an indentation scheme to aid navigation.  

This can be easily done with a TRACE_RETURN(module, return_value) macro

Status:

- **Status:** Pending audit/completion.
- **Next:** Find seed functions that emit `TRACE_START` without a matching `TRACE_END`; ensure every return path is covered, preferably through a common cleanup path where appropriate.

### CPUINFO-PORTABILITY — Update CPUINFO

The detection we have works under all conditions we've tested, and we don't require any more functionality in this area.  But it's based on an older and less sophisticated method than some current implementations.

Gaining access to OpenSSL's API would be the least impactful way to upgrade.  This is a change on their part that would provide wider benefit to the community, and should be recommended to OTC.  There are OSS libraries like Google's `cpu_info` project, but they all add code for limited to no benefit.

Status:

- **Status:** Alternatives noted; no implementation plan approved.
- **Next:** Reassess the current CPU feature-detection requirements and portability constraints, then compare approaches before selecting one.
